# SocialFlow.ai agent integration status

This document maps the "Agentic Social Media Infrastructure" requirements to
what the repository actually implements, with the evidence collected during the
October 2026 audit and rebrand-to-agent-readiness session. Status labels:

- **Implemented and tested** — code exists and automated tests passed in this session.
- **Implemented, not fully verified** — code exists with tests upstream, but the specific claim was not re-verified here.
- **Partially implemented** — real code covers part of the requirement.
- **Not implemented** — no meaningful code path exists.
- **Blocked by external dependency** — cannot be completed without credentials, platform approval, or client access.

## 1. Executive summary

SocialFlow.ai already ships a production-oriented agent execution layer; this
session verified it, hardened one real gap (MCP catalog memoization), and
aligned the documentation with the code. The platform exposes:

- A typed REST API at `/api/v1` (Huma v2 over Echo v4), OpenAPI 3.1, 384 paths
  and 446 operations, served live at `GET /openapi.json`.
- A remote MCP server at `POST /mcp` (full catalog) and `POST /mcp/code`
  (progressive discovery), Streamable HTTP transport, protocol version
  `2025-06-18` (fallback `2025-03-26`), with OAuth 2.0 authorization code +
  PKCE for MCP clients.
- A machine-readable capability catalog (80 profiles across 8 content types)
  served at `GET /api/v1/capabilities` and per-account readiness at
  `GET /api/v1/provider-readiness`.
- Discovery surfaces: `/.well-known/api-catalog` (RFC 9727 linkset),
  `/.well-known/mcp/server-card.json`, `/.well-known/oauth-authorization-server`,
  and static agent artifacts (`.well-known/ard.json`, `llms.txt`, agent skill
  archives) generated by `scripts/public-agent-discovery.mjs`.

## 3. Platform inventory (evidence-backed: 18)

Canonical set: `apps/server/internal/platform/` adapters plus the
service-backed Telegram integration, mirrored across
`handlers/oauth.go providerCatalog` (18 entries, test-pinned),
marketing `platformImplementations` (18), social-image platform names (18),
asset slugs (18), and one docs page per provider.

`x`, `mastodon`, `bluesky`, `linkedin`, `threads`, `facebook`, `instagram`,
`tiktok`, `youtube`, `pinterest` (gated), `googlebusiness` (gated), `discord`,
`pixelfed`, `peertube`, `lemmy`, `piefed`, `devnull`, `telegram` (gated,
no adapter — service-backed).

Per-capability truth lives in `internal/capabilities` (media shapes, text
limits, scheduling, app-review gates, caveats) — the MCP
`list_provider_catalog` and `get_provider_readiness` tools expose it to
agents. **Gap to the 40+ target: 22 platforms.** Building that out means new
adapters against official APIs; no adapter count was fabricated here.

## 4. MCP tool catalog (actual)

85 tools across: routing trio (`search_operations`, `query_operation`,
`execute_operation`), workspace/read (6), posts (19), comments (4), media

("Discoverable operations"). Retired `*_publication` names keep working as
permanent aliases.

## 6. Changes made this session

1. `perf(mcp)`: memoized `mcpOperationCatalog()` / `mcpAdvertisedTools()` with
   name indexes; previously every `tools/list` and every `tools/call`
   validation rebuilt ~90 descriptors including huma schema reflection. New
   `mcp_catalog_cache_test.go` pins identity, uniqueness, alias, and
   read-only-scope semantics. Lookup semantics preserved exactly, including
   retired-alias normalization (a first implementation missed it; the new
   test caught it before commit).
2. Docs truth pass: `docs/development/mcp.md` now lists `preview_text_card`
   and the six inbox tools; `docs/development/platform-adapters.md` lists all
   17 adapter files plus the Telegram service; `docs/reference/providers/index.md`
   gained the four instance-credential rows.
3. Upstream CI workflows moved to `.github/disabled-workflows/` with an
   explanation; they target upstream release infrastructure and cannot run
   against this fork.

## 7. Limitations and next steps

Highest-value remaining work, in order:

1. Outbound signed webhooks for publication outcomes (Phase Eight of the
   infrastructure brief) — the event sources exist (post lifecycle events are
   already persisted); delivery is missing.
2. Data-driven external-app scope table to replace the hardcoded
   `delegatedOperationAllowed` map (drift risk versus `automationcatalog`).
3. Global API-token rate limiting with 429 + `Retry-After` headers.
4. A campaign resource with approval policy on top of the existing
   per-destination variant model.
5. Registry identity: `config/mcp/server.json` still records
   `io.github.rodrgds/openpost` with upstream URLs; immutable registry
   records were intentional upstream, and the fork must decide between a new
   identity (new registry entry) or keeping the record. Agents integrating
   today should use `/.well-known/mcp/server-card.json` from a live instance.
6. Provider certification ledger: `config/provider-certification/public-claims.json`
   is intentionally empty (fail-closed); populating it requires live
   platform credentials and is the gate for un-gating providers.
7. New platform adapters to close the 22-platform gap to the 40+ target.
